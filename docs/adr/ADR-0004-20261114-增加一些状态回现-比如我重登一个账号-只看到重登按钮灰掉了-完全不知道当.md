## 1. 背景与问题定义 (Context & Problem Statement)

- **原始 `/grill-me` 诉求**：/grill-me 增加一些状态回现，比如我重登一个账号，只看到重登按钮灰掉了，完全不知道当前是状态和情况，刷新一下页面连按钮都恢复了，这个体验非常不好

## 2. 决策树访谈记录 (Decision Drivers & Grill-Me Q&A)

#### 决策分支 1（单选）：我已经梳理了当前代码：单账号「重登」目前是同步阻塞请求且未写入账号运行态（RenewState），批量登录的任务 ID 也仅存在前端内存，所以刷新页面或切换菜单就会丢失状态，甚至导致重复点按拉起多个浏览器。

首先确认一下本次「状态回显」希望覆盖的操作范围？

候选方案：
- (Recommended) 全面覆盖：单账号/批量卡密重登、后台自动续期、单账号/全池测活、Token 续期（统一后端运行态，刷新/切页不丢失）
- 聚焦登录与续期：仅针对单账号重登、批量卡密登录与后台自动续期队列做状态持久化与阶段回显
- 仅单行快捷操作：只优化账号列表单行的「重登 / 测活 / 续期」按钮与行内状态反馈

> **已选决策**：(Recommended) 全面覆盖：单账号/批量卡密重登、后台自动续期、单账号/全池测活、Token 续期（统一后端运行态，刷新/切页不丢失）

#### 决策分支 2（单选）：对于耗时最长的「卡密重登/续期」（通常需 20~120 秒），你希望在账号行和顶部任务条看到什么粒度的进度信息？

候选方案：
- (Recommended) 细粒度阶段回显：实时展示具体执行步骤（如「排队中 → 代理预检 → 打开登录页 → 填充邮箱 → 填充密码 → 2FA验证/等待过盾 → 提取Token」及已耗时）
- 粗粒度状态回显：仅区分「排队中 / 重登中 / 测活中 / 续期中」及完成后的成功或失败结果，不展示浏览器内部步骤

> **已选决策**：(Recommended) 细粒度阶段回显：实时展示具体执行步骤（如「排队中 → 代理预检 → 打开登录页 → 填充邮箱 → 填充密码 → 2FA验证/等待过盾 → 提取Token」及已耗时）

#### 决策分支 3（单选）：目前单账号点「重登」是同步长请求（且固定无头模式、未与批量登录互斥）。如果改为后端状态驱动，当你在列表里连续点击多个账号的「重登」（或当前已有登录任务在跑）时，你期望的调度行为是？

候选方案：
- (Recommended) 异步入队串行执行：单账号点「重登」立即转后台任务并复用页面「无头模式」开关；若已有账号在重登，新点的账号自动加入排队（显示「排队中 #N」），避免多开浏览器冲突或报错拒绝
- 异步独立但互斥：单账号点「重登」转后台执行，但若当前已有登录任务运行则直接报错拒绝，不允许追加排队
- 保持同步等待请求返回：点「重登」保持长连接等待直到完成，仅在后端额外记录状态供刷新页面后轮询查看

> **已选决策**：(Recommended) 异步入队串行执行：单账号点「重登」立即转后台任务并复用页面「无头模式」开关；若已有账号在重登，新点的账号自动加入排队（显示「排队中 #N」），避免多开浏览器冲突或报错拒绝

#### 决策分支 4（单选）：关于「全池测活」与单账号「测活 / Token 续期」，你希望达到怎样的交互与刷新恢复效果？

候选方案：

> **已选决策**：(Recommended) 全池测活也改为后端进度追踪 + 行内实时状态：全池测活展示实时进度条（已完成/总数、正常/异常），每个正在被测活或续期的账号行内实时显示「测活中 / 续期中」及耗时，刷新页面自动恢复进度条与行状态

> **已选决策**：(Recommended) 行内阶段徽章 + 按钮常驻状态 + 最近操作摘要：操作中在状态列展示动态阶段徽章与计时（如「重登中 · 2FA验证 18s」），右侧按钮常驻显示「重登中.../排队中...」不再隐藏；完成后保留最近一次操作结果摘要（如「刚刚重登成功」「测活通过 180ms」）

- 任务一结束即收起顶部进度面板，仅通过顶部临时提示条（NoticeBanner）提示一次结果

> **已选决策**：(Recommended) 支持取消排队 + 保留最近任务战报：排队尚未开始的账号支持点击「取消排队」移出队列；顶部任务面板在任务完成后保留最近一次汇总与失败明细（可展开查看、可手动关闭），刷新页面也不丢失战报

## 4. 落地方案与影响范围 (Implementation Plan & Consequences)

# 号池操作全链路实时状态回显与刷新恢复实施计划

## 1. 背景与目标

解决当前号池管理台在执行「单账号重登」「批量卡密登录」「后台自动续期」「单账号/全池测活」「Token 续期」时状态反馈缺失、按钮仅置灰无阶段回显、刷新页面或切换路由后丢失进度与战报的问题。

### 已对齐的核心设计决策
1. **覆盖范围**：全面覆盖单账号/批量卡密重登、后台自动续期（`KamiRenewWorker`）、单账号/全池测活、Token 续期，全部由后端运行态驱动，刷新页面（`F5`）或跨页面切换零延迟恢复。
2. **细粒度阶段回显**：卡密浏览器重登/续期实时回显阶段步骤（`排队等待中` → `代理连通预检` → `启动浏览器` → `打开登录页` → `填充账号邮箱` → `填充登录密码` → `填充 2FA 动态码` / `等待安全验证过盾` → `提取会话 Token`）及当前已耗时。
3. **单账号重登异步入队串行化**：单账号点击「重登」复用页面「无头模式」开关，立即转入后台串行登录任务；若当前已有登录任务在运行，新点击的账号自动追加进队列（显示 `排队中 #N`），避免多开 Chrome 冲突或报错拒绝。
4. **全池测活异步进度追踪**：全池测活支持后台进度追踪（已完成/总数、正常/异常）及各账号行内实时「测活中」状态，刷新页面自动恢复。
5. **行内常驻状态与最近操作摘要**：账号处于操作中时，状态列显示动态阶段徽章与计时，右侧操作区取消 `hover-reveal` 隐藏，常驻展示 `重登中...` / `排队中 #N（可点取消排队）` / `测活中...` / `续期中...`；操作完成后在行内保留最近一次操作结果摘要（如 `刚刚 · 重登成功 · Token 已更新`、`测活通过 · 180ms · 10 模型`）。
6. **支持取消排队与保留战报**：支持取消尚未开始执行的排队账号（单行取消或顶部一键取消剩余排队）；任务完成后顶部战报面板保留最近一次汇总与逐账号失败明细，直到用户手动点击「关闭战报」。
7. **自适应轮询与跨页联动**：`/accounts` 与 `/overview` 内联返回活跃/近期任务快照，有活跃操作时前端自动开启 `1s` 轮询（空闲自动停止），并在左侧栏底部「号池脉搏」与「网关总览」页联动展示正在执行的任务状态。

   - `LastActionOK bool` (`json:"last_action_ok,omitempty"`)
   - `LastActionSummary string` (`json:"last_action_summary,omitempty"`)
   - `LastActionAt string` (`json:"last_action_at,omitempty"`)
3. 在 `toSnapshot(a *Account)` 中映射上述字段（`ActionStartedAt` 与 `LastActionAt` 非零时格式化为 `time.RFC3339`）。

5. 在 `internal/accounts/pool.go` 新增线程安全辅助方法（加锁 `p.mu`）：

## 4. 注意事项与避坑指南（Pitfalls）

1. **`go:embed` 构建顺序**：修改 `web/src/` 后必须先运行 `cd web && npm run build`，否则 `go test ./...` 会使用旧的前端静态产物。
2. **预检全部失败时的任务终态**：在 `StartKamiLoginBatch` 中，如果所有请求的账号在预检阶段就已失败（例如传入的 `missing-account-id` 不存在，见 `TestKamiLoginEndpointReturnsPollableAsyncTask`），`targets` 为空，此时 `runKamiLoginTask` 仍需将 `task.Status` 置为 `"completed"` 并清空 `p.kamiLoginRunning`，确保 `TestKamiLoginEndpointReturnsPollableAsyncTask` 与 `TestKamiLoginBatchTaskUpdatesPreflightResults` 100% 兼容通过。
3. **锁顺序与并发安全**：`ChatGPTProvider.kamiLoginMu` 与 `accounts.Pool.mu` 切勿交叉死锁——在更新 `KamiLoginTask` 与调用 `p.pool.SetAccountActionState` 时，避免在持有 `p.kamiLoginMu` 锁的同时调用可能反过来请求 `kamiLoginMu` 的方法（`Pool` 方法只锁 `Pool.mu`，不依赖 `provider`，因此单向调用安全，但尽量在锁外或明确单向锁序下调用）。
