## 1. 背景与问题定义 (Context & Problem Statement)

- **原始 `/grill-me` 诉求**：/grill-me-adr chat 现在比较简单，没有历史会话等功能，调研其他优秀专业成功的chat 产品，增强功能完整性，另外是否需要集成其他类型的中间件数据库，向量数据库，lancedb 等等

## 2. 决策树访谈记录 (Decision Drivers & Grill-Me Q&A)

#### 决策分支 1（单选）：关于历史会话的消息组织结构，你倾向于采用哪种模型？

候选方案：
- (Recommended) 经典线性多会话模型（Linear History）：类似经典 ChatGPT / TypingMind，每个会话按时间平铺，支持重试/重新生成与复制，数据结构精炼、前后端同步与分页性能极高
- 完整分支树模型（Conversation Tree / Forking）：类似 Claude / LibreChat，支持在历史任意消息节点编辑并产生 1/2、2/2 分支版本，适合复杂创作回溯，但前端树状渲染与存储逻辑较复杂

> **已选决策**：(Recommended) 经典线性多会话模型（Linear History）：类似经典 ChatGPT / TypingMind，每个会话按时间平铺，支持重试/重新生成与复制，数据结构精炼、前后端同步与分页性能极高

#### 决策分支 2（单选）：关于中间件数据库、向量数据库（如 LanceDB）的集成策略与边界：在严格零 CGO 与单二进制发布约束下，你倾向于何种方案？

候选方案：
- (Recommended) 零外部中间件原则（基于现有纯 Go SQLite + FTS5 全文搜索）：坚守零 CGO 与单二进制极简部署，拒绝引入依赖 C-FFI 的嵌入式 LanceDB 或额外 Redis 进程，用毫秒级全文检索覆盖 99% 的历史会话查找需求
- 插件化向量库扩展架构（默认零中间件，环境变量可选外接 Qdrant / PGVector / Milvus）：核心系统保持零依赖，为有重型企业知识库/RAG 诉求的场景预留 VectorStore 适配器接口，用户自选配置
- 纯前端本地向量计算（Local-First + Transformers.js）：在浏览器端用 WebAssembly 计算小模型 Embedding，无需后端引入任何向量中间件即可实现本地对话语义搜索

> **已选决策**：插件化向量库扩展架构（默认零中间件，环境变量可选外接 Qdrant / PGVector / Milvus）：核心系统保持零依赖，为有重型企业知识库/RAG 诉求的场景预留 VectorStore 适配器接口，用户自选配置

#### 决策分支 3（单选）：关于会话数据的持久化与多端同步架构，你期望采用哪种模式？

候选方案：
- (Recommended) 服务端 SQLite 持久化 + 前端 IndexedDB 双写缓存（Hybrid Sync）：服务端为主数据源，支持跨端/跨浏览器同步；本地做 IndexedDB 离线缓存与即时渲染，断网或网络抖动也能流畅浏览历史
- 纯服务端主导（Server-First）：所有会话列表与消息均从后端 REST API 分页拉取，保证多设备访问绝对一致，逻辑最单一清晰
- 客户端本地优先（Local-First，类似 TypingMind）：数据默认保存在用户当前浏览器 IndexedDB，通过手动导入/导出 JSON、Markdown 备份，后端零存储压力

> **已选决策**：(Recommended) 服务端 SQLite 持久化 + 前端 IndexedDB 双写缓存（Hybrid Sync）：服务端为主数据源，支持跨端/跨浏览器同步；本地做 IndexedDB 离线缓存与即时渲染，断网或网络抖动也能流畅浏览历史

#### 决策分支 4（多选）：增强 Chat 功能完整性时，本次优先纳入哪些高价值功能模块？（可多选）

候选方案：
- (Recommended) 完善的会话组织抽屉：左侧边栏按时间分组（今天、昨天、过去7天、更早）、会话重命名、置顶（Pin）、批量管理与删除
- (Recommended) 会话导入与导出：支持导出为 Markdown、JSON 或纯文本，支持导入历史对话或从 ChatGPT 导出的数据备份
- (Recommended) 消息级高频交互：编辑上一轮提问、切换模型重新生成、流式生成实时中断（Stop Generating）、消息一键复制、Token 消耗与耗时展示
- (Recommended) 预设角色与系统提示词（Presets / Prompt Templates）：支持自定义系统提示词，内置代码助理、翻译专家、平台诊断 Copilot 等预设角色一键切换
- (Recommended) 平台专属特性深度融合：保留并强化现有的 `/diagnose`、`/fix` 根因排障与 OpenUI 动态 DSL 卡片渲染能力，普通对话与智能运维自愈无缝结合
- 联网检索与引用卡片（Web Search）：集成 DuckDuckGo / Tavily 或后端代理联网提示词注入，回答中展示网页引用角标与来源链接

#### 决策分支 5（单选）：关于历史会话的搜索与回溯能力，你希望达到何种体验深度？

候选方案：
- (Recommended) 毫秒级多会话即时全文检索（前端 MiniSearch 倒排索引 + 后端 SQLite FTS5）：支持根据关键词秒级检索所有历史会话消息内容，高亮关键字并一键直达上下文
- 混合检索引擎（全文检索 + 纯 Go 内存向量余弦相似度）：既支持精准关键词命中，又支持小规模语义相似匹配，且完全零 CGO、无外部服务依赖
- 极简标题模糊搜索与分页：仅支持在左侧边栏按会话标题进行即时过滤筛选，暂不开启深层消息内容全文索引

> **已选决策**：(Recommended) 毫秒级多会话即时全文检索（前端 MiniSearch 倒排索引 + 后端 SQLite FTS5）：支持根据关键词秒级检索所有历史会话消息内容，高亮关键字并一键直达上下文

# 生产级专业 AI 对话工作台（Chat Studio）与插件化向量扩展设计规范

## 1. 概述与背景 (Overview & Objectives)

在当前版本中，AI-Web-Free 控制台的对话功能（`#/chat`，即 `GenerativeWorkbench.tsx`）主要扮演两重角色：
1. 智能运维 Copilot（处理 `/diagnose`、`/fix` 等平台根因诊断自愈指令）；
2. Thesys OpenUI 动态卡片 DSL 渲染器。

然而，现有实现仅将对话暂存在单一 `session_key="default"` 的全局槽位中，缺少会话列表与组织抽屉，不支持会话历史回溯、重命名、置顶、导入导出；消息级交互亦缺少重新生成、流式打断（Stop）、Token 消耗与联网引用来源展示。

本规范旨在将 `#/chat` 升级为对标业界顶尖产品（ChatGPT、Claude、TypingMind、Open WebUI）的**全功能、高生产力专业 AI 对话工作台（Chat Studio）**，并在**严格恪守系统零 CGO 与单二进制发布红线**的前提下，确立历史检索与向量数据库的工程边界。

### 2.1 业界优秀产品调研矩阵

| 标杆产品 | 核心架构特征 | 交互亮点 | 本项目采纳策略 |
| :--- | :--- | :--- | :--- |
| **ChatGPT / Claude.ai** | 云端微服务 + SSE 流式 + 会话树 | 按时间维度（今天/昨天/7天前）分组、中途随时中断生成、编辑上一轮提问、引用来源浮层 | 采纳其经典会话组织抽屉、消息中途打断、提问编辑与重新生成交互 |
| **Open WebUI** | Python FastAPI + SvelteKit + SQLite/Chroma | 会话管理抽屉、角色预设广场（Presets）、模型横向对比、多模态附件 | 采纳预设角色模板体系与侧边栏折叠抽屉，舍弃其重型 Python/Chroma 依赖 |
| **LibreChat** | Node.js + MongoDB + Redis + MeiliSearch + pgvector | 深度会话分支树（Forking）、插件系统、完整导入导出 | 采纳 Markdown/JSON 导入导出格式，避免其繁复的重型中间件矩阵 |
| **TypingMind** | Local-First 纯前端 + IndexedDB + 本地倒排索引 | 毫秒级极速响应、离线可用、按文件夹/标签分类、纯内存全文搜索 | 采纳 Local-First 理念与前端毫秒级倒排索引，与服务端 SQLite 组成双写镜像 |

### 2.2 中间件与向量数据库（LanceDB）选型剖析

针对是否引入 LanceDB、Redis 或外部向量数据库的重大疑问，规范确立以下准则：

1. **坚决排斥嵌入式 LanceDB（红线约束）**：
   - 本项目核心红线：`CGO_ENABLED=0` 纯静态编译，基于 `distroless/static-debian12:nonroot`。
   - LanceDB 底层为 Rust 开发，其 Go SDK 依赖 CGO / C-FFI 绑定。在纯静态编译模式下**无法构建**。
   - 强行引入 LanceDB 独立容器会极大增加用户部署门槛，违背单二进制极简私有化交付原则。
2. **全文检索（FTS）优先覆盖 99% 的核心诉求**：
   - 历史会话查找的核心场景为精准定位特定代码、报错、配置等字词（例如搜索包含“dockerfile”或“turnstile”的会话）。
   - 纯 Go SQLite 原生 FTS5 或前端 MiniSearch 倒排索引在**零外部中间件、零额外开销**下即可实现毫秒级高亮检索，性价比远超向量检索。
3. **插件化 VectorStore 适配器模式（可扩展但不强绑）**：
   - 后端抽象标准 `VectorStore` 驱动接口。
   - 默认启用 `memory` / `sqlite` 纯 Go 基础驱动（零 CGO，基于余弦相似度）。
   - 环境变量可选外接企业已有的 `qdrant` / `pgvector` / `milvus`（基于 HTTP REST 客户端通信，无 CGO 依赖），按需开启。
